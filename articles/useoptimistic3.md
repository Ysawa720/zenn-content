## はじめに

`useOptimistic` についての記事3本目です。

1. [タップ即反映UIを作った話](https://zenn.dev/ysaya_dev/articles/react-useoptimistic) … `useOptimistic` + `useTransition` でタップ即反映を実装した
1. [導入して、結局外した話](https://zenn.dev/ysaya_dev/articles/useoptimistic2) … 手動 state 管理との二重カウントにぶつかり、外す判断をした

2本目で「Client Component で base state を手動 `setState` 管理すると相性が悪い」と書きました。でも、書いたあとで気持ち悪さが残りました。「同一コミットに乗らないから」と説明したものの、自分でも何が同じコミットに乗らないのか、ちゃんと言葉にできていなかったからです。

そこで、`0 → 1 → 2 → 1` というチラつきがなぜ起きるのかを、レンダリングのタイミングまで分解して考え直してみました。結果として何度も自分の理解を引っくり返すことになったのですが、最終的に「手動 state 管理では base 反映とキュー破棄が原理的に別コミットになる」という納得のいく結論に着地できました。

途中で考え違いをしている箇所もそのまま残します。同じところでつまずく人の役に立つかもしれないので。

## おさらい：わかっていたこと

2本目までで自分の中で確定していたことは3つです。

`useOptimistic(base, updater)` は、第1引数の **base state** と、`addOptimistic` で積んだ **pending な楽観エントリのキュー** を、`updater` で合成して値を返す。

キューが破棄されるのは、`startTransition` のブロック全体が完了したとき。

そして、つまずいた構成はこれでした。

```jsx
const [pitches, setPitches] = useState([]);
const [optimisticPitches, addOptimisticPitches] = useOptimistic(
  pitches,
  (state, newPitch) => [...state, newPitch]
);

startTransition(async () => {
  addOptimisticPitches(newPitch);       // ①
  const id = await recordPitch(...);    // ②
  setPitches([...pitches, realPitch]);  // ③
});
```

症状は、ストライクをタップしたときにカウントが `0 → 1 → 2 → 1` とチラつくことでした。

## まず引っかかったこと：actual value は誰が更新するのか

そもそもの話として、`useOptimistic` 自身は第1引数（actual value）を書き換える手段を持っていないことに気づきました。返ってくるのは `[optimisticValue, addOptimistic]` の2つだけで、`addOptimistic` はキューに積むだけ。**actual value を更新する責任は `useOptimistic` の外側にある**わけです。

外側というのは、自分の構成だと `setPitches` のことです。一方、Server Components 構成なら、Server Action が `revalidatePath` を呼んで Server Component を再実行させ、新しい値が props として降ってくる。この場合は自分で `setState` を呼ばない。

「同じ `useOptimistic` でも、actual value を更新する主体が構成によって違う」。ここが今回の長い回り道の入り口でした。

## 回り道1：完了後に値が一瞬戻らないか？

最初に疑ったのはこれです。`useOptimistic` が「キュー破棄」と「actual value 更新」を別々にやるなら、その隙間で値が一瞬戻るのでは、と。

考えた結論は「今回は戻らない」。`setPitches` が `startTransition` の**内側**にあるから、transition の一部として完了と一緒に扱われる、と理解しました。

……ただ、この「内側だから大丈夫」という理解は、あとで自分でひっくり返すことになります。このときはまだ気づいていませんでした。

## 回り道2：`await` の時間が悪さをしているのか？

次に疑ったのが `await`（DB通信）の所要時間です。「通信が遅いから、二重に見える時間も伸びるんじゃないか」と。

これは**勘違い**でした。時系列で並べてみて気づきました（初期 base=0球）。

```
①の直後   base=0球  キュー=[1球]  合成=1球   ← タップ即反映
②の最中   base=0球  キュー=[1球]  合成=1球   ← await でサーバー待ち
③の直後   base=1球  キュー=[1球]  合成=2球   ← ★二重!
完了時     base=1球  キュー=破棄    合成=1球   ← 1球に戻る
```

`2球` が見えるのは「③のコミット」から「完了のコミット」までの区間です。③は `await` の**後ろ**にあるので、③から完了までに `await` は挟まらない。つまり `2球` が見える長さは `await` とは無関係。

`await` が伸ばすのは①（`1球`）が出ている時間だけ。二重を**生んでいる**のは③で base を増やしたことであって、`await` の長さは二重の発生にも可視時間にも関係しない。ここで一つ、はっきり腑に落ちました。

## 回り道3：手動更新なら必ずチラつくのか？

「じゃあ手動更新だと必ずチラつくのか」と考えて、これは「素朴な追加 updater のままなら起きるが、必ずではない」と気づきました。`updater` を「追加」ではなく「置き換え」にすれば防げる。1本目・2本目でも触れた `tempId` です。

```jsx
const [optimisticPitches, addOptimisticPitches] = useOptimistic(
  pitches,
  (state, newPitch) => {
    const exists = state.some((p) => p.tempId === newPitch.tempId);
    if (exists) {
      return state.map((p) => (p.tempId === newPitch.tempId ? newPitch : p));
    }
    return [...state, newPitch];
  }
);
```

`tempId` はサーバー処理の**前**にクライアントで生成する識別子です。`pitchId`（サーバー採番）は楽観エントリを作る時点ではまだ存在しないので、楽観エントリと実データを突き合わせられる共通キーは `tempId` しかない、という点も自分の中で整理できました。

③で base に `tempId:'abc'` 付きの実データが入ると、updater が「同じ `tempId` はもう base にある」と判断して置き換える。配列の長さが変わらないので `2球` にならない。

```
①コミット   base=空        キュー=[abc] → 合成1球
③コミット   base=[abc付き]  キュー=[abc] → 置き換え → 合成1球  ← 2球にならない
完了コミット base=[abc付き]  キュー破棄    → 合成1球
```

中間フレームでも合成結果が変わらないようにして、チラつきを吸収する。これは手動更新のままでも使える手だとわかりました。

## ここでひっくり返った：同一コミットに乗ると思い込んでいた

ここが今回いちばん引っかかった部分です。

「`setPitches` が transition 内にあるなら、base 更新とキュー破棄は同じコミットに乗るのでは？ 乗るなら `2球` の中間フレームは存在しないはずだ」。最初はそう考えました。

でも、これは間違いでした。`setPitches` を transition 内で呼んでも、それは「state 更新」という、それ自体でレンダリングを引き起こす操作です。React はまず「**新しい base + まだ破棄されていない楽観キュー**」でレンダリングして反映する。これが `2球` のコミット。そのあと transition が完了してキューが破棄され、もう一度レンダリングされて `1球` に戻る。

```
③コミット(base反映)  →  完了コミット(キュー破棄)
   合成=2球                 合成=1球
```

`setPitches` が transition 内にあっても、「base を反映するレンダリング」が「キュー破棄を反映するレンダリング」に**先行する**。両者は別コミットなので、間に `2球` が挟まる。

自分は「transition の管轄に入る」ことと「同じコミットで反映される」ことを混同していました。回り道1で「内側だから大丈夫」と思ったのは、この取り違えが原因でした。

## たどり着いた結論：手動更新では原理的に2コミットに分かれる

ここまで分解して、ようやく納得できました。

**手動 `setState` では、base 反映を transition 完了（キュー破棄）と同一コミットには載せられない。** `setState` は base 更新が「独立した操作」である以上、それを反映するレンダリングが、キュー破棄のレンダリングより必ず一手先行する。だから `2球` の中間フレームは原理的に生じる。

Server Components + `revalidatePath` 構成がこれを避けられる理由も、ここで腑に落ちました。あの構成では、base の更新が「`setState` という独立操作」ではなく、「**transition の完了によるサーバー再レンダリングの結果そのもの**」です。base が新しくなることとキューが破棄されることが、同じ1つの完了イベントの中で同時に起きる。だから中間フレームが生まれない。

手動 `setState` は base 更新が独立操作である以上、構造的にこれと同じことはできない。これが「手動 state 管理と相性が悪い」の、自分なりに納得できた中身でした。

## まとめ

|自分が引っかかった問い                 |たどり着いた答え                                   |
|----------------------------|-------------------------------------------|
|`await` の長さは二重の発生に関係する？     |しない。二重は③で base を増やした時点で確定する                |
|`await` の長さは二重が見える時間に関係する？  |しない。`2球` の区間は `await` の外側にある               |
|手動更新だと必ずチラつく？               |素朴な追加 updater なら起きる。置き換え（tempId）で吸収できる     |
|base 反映とキュー破棄を同一コミットに載せられる？ |手動 `setState` では載せられない（原理的に2コミットに分かれる）     |
|なぜ Server Components 構成だと平気？|base 更新が transition 完了そのものとして起き、同一コミットになるから|

手動 state 管理でチラつきを消すなら、`tempId` の置き換え updater で「中間フレームでも合成結果が変わらない」ようにする一択。コミットを1つにする道は手動更新では塞がれているので、updater 側で吸収するしかない。

ここまで来て、2本目で `useOptimistic` ごと外す判断をした理由が、自分の中で一段はっきりしました。手動更新を真実（source of truth）にする限り、「2コミットに分かれる」という構造的制約からは逃げられず、`tempId` で対症するしかない。それなら source of truth をサーバーかローカルDBの一か所に寄せて、base 更新が自然に一元化される構成にしたほうが、制約そのものが消える。2本目で「外す」と決めたときは直感的な判断でしたが、今回その判断の裏付けを自分の手で取れた感覚があります。

## 振り返って

正直、この理解にたどり着くまでに何度も考えを引っくり返しました。「内側だから同一コミット」→「`await` が見せている」→「いや `await` は無関係」→「同一コミットに乗る」→「乗らない、先行するだけ」→「やはり原理的に2コミット」という具合です。

遠回りでしたが、`useOptimistic` みたいに「レンダリングのタイミング」と「コミットの単位」が絡む話は、言葉を一つずつ正確にしないと簡単に取り違えると痛感しました。自分の場合、「transition の管轄に入る」と「同じコミットで反映される」を切り分けられたのが、最後の決め手でした。表面的に「動いた／動かない」で済ませず、なぜそう動くのかを追うのは時間がかかりますが、こうして一段深く理解できると、次に似た問題に出会ったときの足場になる気がしています。
