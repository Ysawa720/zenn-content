## はじめに

JavaScript を勉強していて、こんなコードに出会いました。

```js
[..."abc"]   // ["a", "b", "c"]
```

文字列にスプレッド構文を適用すると、1文字ずつを要素に持つ**配列**が返ってくる。
これを見て、私はふと思いました。

> **「ということは、文字列って配列なの？」**

結論から言うと **「いいえ」** なのですが、この素朴な疑問を出発点に掘り下げていったら、`Symbol.iterator` という JavaScript の根っこにある仕組みまでたどり着きました。

この記事は、そのときの「なぜ？」を順番に追体験する形でまとめたものです。同じところで引っかかった人の助けになれば嬉しいです。

## Q. 文字列は配列なの？

スプレッド構文で配列になるなら、文字列も配列の一種なのでは——と考えたくなります。
でも、実際に確かめてみると違いました。

```js
const s = "abc";

Array.isArray(s);  // false
s.push("d");       // TypeError: s.push is not a function
s.map();           // TypeError（map は配列のメソッド）
```

配列なら当然使えるはずの `push` や `map` が、文字列では一切使えません。
文字列にあるのは `length` とインデックスアクセス（`s[0]`）くらいで、これは「配列っぽい見た目」を持っているだけでした。

ではなぜ、配列でもないのにスプレッド構文で展開できるのでしょう？

## A. スプレッド構文は「配列」ではなく「イテラブル」を展開する

ここが最初の気づきでした。

スプレッド構文は「**配列を展開する機能**」だと思い込んでいたのですが、正しくは「**イテラブル（反復可能なもの）を展開する機能**」だったのです。

```js
[..."abc"]              // ["a", "b", "c"]   文字列
[...[1, 2, 3]]          // [1, 2, 3]          配列
[...new Set([1, 2])]    // [1, 2]             Set
[...new Map()]          // []                 Map
```

配列も Set も Map も、そして文字列も、共通して「イテラブル」という性質を持っています。
スプレッド構文はその共通の仕組みに従って中身を取り出しているだけ。**配列だから展開できるのではなく、イテラブルだから展開できる**、というわけです。

## そもそも「イテラブル」とは何か

イテラブル（iterable / 反復可能オブジェクト）とは、ざっくり言うと **`for...of` で1つずつ取り出せるオブジェクト** のことです。

もう少し正確に言うと、**`Symbol.iterator` という名前のメソッドを持っているオブジェクト**がイテラブルです。
`for...of` もスプレッド構文も `Array.from()` も、内部ではこのメソッドを呼んで中身を取り出しています。

```js
"abc"[Symbol.iterator]       // function（持っている → イテラブル）
({ a: 1 })[Symbol.iterator]  // undefined（持っていない → イテラブルではない）
```

プレーンなオブジェクト `{}` はこのメソッドを持たないので、`for...of` で回そうとするとエラーになります。

```js
for (const x of [1, 2, 3]) {}   // OK
for (const x of { a: 1 }) {}     // TypeError: is not iterable
```

## 自分でイテラブルを作ってみる

「`Symbol.iterator` を持っていればイテラブル」なら、自分で実装すればどんなオブジェクトでもイテラブルにできます。

```js
const range = {
  from: 1,
  to: 3,
  [Symbol.iterator]() {
    let current = this.from;
    const last = this.to;
    return {
      next() {
        return current <= last
          ? { value: current++, done: false }
          : { value: undefined, done: true };
      }
    };
  }
};

[...range]   // [1, 2, 3]
```

`next()` を呼ぶたびに `{ value, done }` を返し、`done: true` になったら終了する。
これが「イテレータ」の正体です。イテラブルとは、この `next()` を持つイテレータを `Symbol.iterator` 経由で渡してくれる存在、と捉えると腑に落ちました。

### 寄り道：`[Symbol.iterator]() {}` の `[]` `()` `{}` って何？

上のコードを初めて見たとき、`[]` `()` `{}` が連続していて「これは関数？」と混乱しました。
分解すると、それぞれ別の役割を持っています。

- `[Symbol.iterator]` … `[]` は**計算されたプロパティ名**。メソッド名を「固定の文字列」ではなく「変数が指す値」で決める書き方。
- `()` … このメソッドの**仮引数リスト**（この例では引数なし）。
- `{ }` … このメソッドの**処理本体（ブロック）**。

つまり `[Symbol.iterator]() { ... }` 全体で「**`Symbol.iterator` という名前のメソッドを定義する**」という1つのまとまりです。

なぜ `[]` で囲むかというと、`Symbol.iterator` は文字列ではなく**特別な値（シンボル）**なので、メソッド名として直接書けないからです。

```js
const key = "hello";
const obj = {
  [key]() { return "hi"; }   // key の中身 "hello" がメソッド名になる
};
obj.hello();                 // "hi"
```

## ジェネレータを使うと、もっと簡潔に書ける

`range` では `next()` も `{ value, done }` も自分で書きました。これを**ジェネレータ**（`*` と `yield`）で書くと、ぐっと短くなります。

```js
const myIterable = {
  *[Symbol.iterator]() {
    yield 1;
    yield 2;
    yield 3;
  },
};

[...myIterable]   // [1, 2, 3]
```

> この記事ではジェネレータ（`*` と `yield`）そのものの仕組みには深入りしません。自分もまだ深く理解できていないためで、ここでは「`next()` と `{ value, done }` を手書きする代わりに、iterator を自動で作ってくれる便利な書き方」という理解にとどめます。ジェネレータ自体は別途あらためて掘り下げる予定です。

このコードには、ここまでで学んだことが全部詰まっています。順番にほどいていきます。

### 1. このコードの全体像

自作のオブジェクトに「組み込みの鍵」を実装することで、反復可能（iterable）にしているコードです。
**組み込みなのは `Symbol.iterator` の部分だけ**で、`myIterable` という名前も中身の `yield 1, 2, 3` もすべて自作・自由です。器は自分で用意し、鍵だけはエンジンと共有する、というイメージです。

### 2. 計算プロパティ名（ブラケット記法）

キーを `[ ]` で囲むと、**中の式を評価した結果がキーになります**。
`Symbol.iterator` は文字列ではなくシンボル値なので、その値をキーにするには `[ ]` で囲む必要がありました。さきほどの「寄り道」で見た `[key]() {}` と同じ仕組みです。

> ここでいう「キー」は、プロパティもメソッドも区別なく指します。そもそも JavaScript ではメソッドは「値が関数であるプロパティ」にすぎず、中身はすべて「キーと値のペア」だからです。`[key]: "値"` でも `[key]() {}` でも、`[ ]` の中を評価してキーにする点は同じです。

### 3. `Symbol.iterator` とは

ECMAScript 仕様が定めた `Symbol` の静的プロパティで、**well-known symbols（既知のシンボル）** の一つです。
どこで参照しても同じ唯一のシンボル値を指すため、自作コードとエンジン（`for...of` など）が**同じ鍵を共有**できます。

なお名前は `iterator` です（`iterable` や `Symbol.iterable` は存在しません）。最初よく混同しました。

### 4. iterable になる条件（2段階）

鍵を定義するだけでなく、次の2段階を満たす必要があります。

1. **`Symbol.iterator` をキーに持つメソッドを定義する**（iterable の条件）
1. **そのメソッドが、`next()` を持ち `{ value, done }` を返す iterator を返す**（iterator の条件）

`range` ではこの2段階を手書きしました。
ジェネレータ（`*` と `yield`）を使うと、**この iterator を自動生成**してくれるため、`next()` や `{ value, done }` を自前で書かずに済みます。`yield` した値が順に `value` として流れ、`yield` し尽くすと自動的に `done: true` になる、という対応です。

### 5. プロパティの値の正体（3つの層）

同じ `myIterable[Symbol.iterator]` でも、`()` を付けるかどうかで指すものが変わります。ここが整理できると一気にクリアになりました。

|書き方                            |正体                                     |
|-------------------------------|---------------------------------------|
|`Symbol.iterator`              |鍵（シンボル値）                               |
|`myIterable[Symbol.iterator]`  |その値 ＝ **ジェネレータ関数**                     |
|`myIterable[Symbol.iterator]()`|呼び出した戻り値 ＝ **ジェネレータオブジェクト（＝ iterator）**|

実際に確かめると、3層がはっきりします。

```js
typeof Symbol.iterator                      // "symbol"   鍵
typeof myIterable[Symbol.iterator]          // "function" ジェネレータ関数
const it = myIterable[Symbol.iterator]();
it.next();                                  // { value: 1, done: false }
```

### 6. 何に使えて、何に使えないか

`Symbol.iterator` を実装すると、`for...of`・スプレッド `[...x]`・分割代入・`Array.from`・`new Map`/`new Set` などで使えるようになります。

```js
for (const n of myIterable) {}     // OK
[...myIterable]                    // [1, 2, 3]
const [a, b] = myIterable;         // a=1, b=2
Array.from(myIterable)             // [1, 2, 3]
```

ただし `.map()` などの**配列固有メソッドは使えません**。それらは `Array.prototype` 上にあるメソッドで、iterable であることとは別だからです。使いたい場合は一度配列に変換します。

```js
myIterable.map(x => x * 2)          // TypeError
[...myIterable].map(x => x * 2)     // [2, 4, 6]（配列にしてから）
```

これは、最初に確かめた「**文字列は配列のメソッドを持たない**」のとまったく同じ理屈です。iterable であることと、配列であることは別物——という最初の気づきが、ここでもう一度効いてきます。

### 7. Symbol 型そのものについて

最後に、鍵そのものである `Symbol` 型の話です。
シンボルは文字列・数値などと同じ**プリミティブ型**（全7種の一つ）です。ただし文字列と違い、**生成するたびに必ず一意になります**。

```js
Symbol("desc") === Symbol("desc")   // false（説明が同じでも別物）
```

内部的には「内容」ではなく「**一意な実体としての同一性（参照的な比較）**」で識別され、メモリ上の具体的な表現は仕様未規定でエンジン依存です。
だからこそ「他の誰とも衝突しない鍵」として使えて、`Symbol.iterator` のような well-known symbol が「唯一の共有鍵」として機能するわけです。

> JavaScript のプリミティブ型は全7種：`string` / `number` / `boolean` / `bigint` / `undefined` / `null` / `symbol`。`symbol` だけ「一意性」という他にない性質を持っているのが面白いところです。

### このコードの本質を一言で

> **自作のオブジェクト（器）に、エンジンと共有する唯一の鍵 `Symbol.iterator` を実装し、そこにジェネレータで iterator を返させることで、そのオブジェクトは iterable になる。**

これが冒頭コードの正体でした。

## 文字列も、自作した range とまったく同じ構造だった

ここまで来ると、文字列の正体が見えてきます。
文字列にも `Symbol.iterator` が備わっていて、`range` と同じように手動で `next()` を呼び出せます。

```js
const s = "abc";
const it = s[Symbol.iterator]();

it.next();   // { value: "a", done: false }
it.next();   // { value: "b", done: false }
it.next();   // { value: "c", done: false }
it.next();   // { value: undefined, done: true }
```

自分で実装した `range` と、組み込みの文字列。返ってくる形は同じです。

```js
range[Symbol.iterator]().next()   // { value: 1,   done: false }
"abc"[Symbol.iterator]().next()   // { value: "a", done: false }
```

文字列は「最初からイテラブルとして実装済みのオブジェクト」だっただけ。
だから、イテラブルを扱う仕組みはすべて文字列にも等しく使えます。

```js
[..."abc"]              // ["a", "b", "c"]   スプレッド
Array.from("abc")       // ["a", "b", "c"]   Array.from
for (const c of "abc")  // "a", "b", "c"      for...of
const [x, y] = "abc";   // x="a", y="b"       分割代入
```

最初の疑問「文字列は配列か？」の答えはこうなります。

> **いいえ。文字列は配列ではないが、配列と同じ `Symbol.iterator` の仕組み（イテラブル）を持っている。**

`push` や `map` といった配列のメソッドは持たないけれど、イテラブルとしての顔だけは共通している。だからスプレッドできたのです。

## おまけ：この仕組みが効いてくる「文字数カウント」

実はこの話、実用的な場面につながります。サロゲートペアを含む文字列の**正しい文字数**を数えるケースです。

JavaScript の文字列は内部的に UTF-16 で、`.length` は「文字の数」ではなく「**コード単位（16ビット単位）の数**」を数えます。絵文字など一部の文字は2コード単位（サロゲートペア）で表現されるため、`.length` ではズレます。

```js
const emoji = "😀";
emoji.length;          // 2  ← コード単位で数えるので 2 になる
[...emoji].length;     // 1  ← 正しい
```

なぜスプレッドだと正しく数えられるのか。
文字列の `Symbol.iterator` は、`next()` が**コード単位ではなくコードポイント単位**で値を返すように作られているからです。サロゲートペアを1文字としてまとめて取り出してくれます。

```js
[..."😀"]      // ["😀"]    （長さ 1）
"😀"[0]        // "\ud83d"  （インデックスアクセスだと壊れた断片）
```

整理すると、こうです。

- `str[i]` / インデックスアクセス → **コード単位**ベース（サロゲートペアが割れる）
- `for...of` / スプレッド / `Array.from()` → **コードポイント単位**ベース（正しく1文字ずつ）

なので、サロゲートペアを含むかもしれない文字列を正しく数えたいときは、こう書きます。

```js
const str = "吉野家";
console.log([...str].length);  // 3
```

`吉野家` 自体は3文字とも基本範囲なので `.length` でも 3 になりますが、「どんな文字でも正しく数えられる書き方」としてはスプレッドが安全、というわけです。

## まとめ

「文字列は配列なの？」という素朴な驚きから始まり、こんな道筋をたどりました。

1. 文字列は配列ではない（`push` や `map` は使えない）
1. でもスプレッドできるのは、スプレッドが「イテラブル」を展開する仕組みだから
1. イテラブルとは `Symbol.iterator` を持つオブジェクトのこと
1. 自分でも `Symbol.iterator` を実装すればイテラブルを作れる（`next()` と `{ value, done }` を返す）
1. ジェネレータ（`*` / `yield`）を使えば、その iterator を自動生成できて簡潔に書ける
1. `Symbol.iterator` は「エンジンと共有する唯一の鍵」。`symbol` 型の一意性がそれを支えている
1. 文字列はそれを最初から実装済みのオブジェクトだった
1. しかもコードポイント単位で取り出すので、文字数カウントにも効いてくる

`[..."abc"]` の一行の裏に、これだけの仕組みが隠れていました。
「なぜそう動くのか」を一段掘ると、点が線でつながっていく感覚があって、これが面白いところだなと思います。
